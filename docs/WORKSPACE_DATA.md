# Live workspace records

Apply `supabase/migrations/202609260002_workspace_records.sql` once, after the already-applied auth migration, using the Supabase SQL Editor. Do not rerun the first migration.

The signed-in app now reads and writes real artists, releases, and tasks. It does not load any sample records from localStorage. The public `/demo` continues using sample data independently. Inbox, approvals, and Dopio show connection/empty states until their integrations exist.

The migration adds a UUID `record_id` to artists without changing existing primary keys, which may be UUID or numeric. New releases and tasks use this stable key. Composite foreign keys enforce that the artist, release, and task belong to the same workspace and that a task's artist matches its release. Workspace ownership cannot be changed through record-edit requests. Only validated business fields are writable.

Create, edit, archive, and task completion are server actions that authenticate again, derive workspace membership server-side, and rely on database RLS for final enforcement. Activity is generated by database triggers in the same transaction; users cannot forge or edit the activity feed. Dates in the overview/calendar use the saved workspace timezone (America/Chicago after migration 033). No simulated events or future dates are added to undated records.

With migration 020, the app archives artists, projects, and tasks. History remains available and Company controls can restore archived records. Archiving a parent hides its linked work without deleting it. Calendar cleanup requires a separate preview and approval.

Read errors show a retry state rather than pretending a failed request returned an empty workspace. Write errors keep the form values so the user can retry. If a write succeeds but reloading fails, the app explicitly asks for a refresh before retrying. List reads paginate through the PostgREST default row limit.

### Remaining product and release risks

- **Before external pilot:** verify hosted migrations, two real accounts with different roles, fresh signup, OAuth expiry/reconnect, one approved test send and one approved Calendar sync. Test rejected/uncertain sends without resending. Verify backup restoration and operational error monitoring before relying on production records.
- **Activation:** brief import requires explicit headings and text/Markdown; no PDF/Word ingestion. Re-import does not update/merge existing artists. Contacts conflict as a batch. Review edits are not durable across refresh even though source briefs can be saved. Invite acceptance is buried in Company controls after initial onboarding. These need observed manager usability sessions.
- **Daily usefulness:** no unified “waiting on whom / what needs my decision” inbox; historical send counts are not delivery or up-to-date notification status. Calendar and email remain separate, explicit actions after edits. “Releases” naming/statuses still leak into tour/campaign views. General tasks are not part of project Calendar sync.
- **Scale:** workspace loading fetches all artists, tasks, imported message bodies and activity into the client, and several operational panels have explicit row caps. Add server-side paging/lazy loading before larger company imports. Exports are sequential reads, not a transactionally consistent database backup.
- **Access model:** workspace roles do not provide artist-level confidentiality. Any workspace member can read the workspace's business records, imported emails and audit history. This must match the pilot company's expectations.
- **Reliability:** local PGlite tests do not establish real concurrent PostgreSQL transaction behavior or delivery guarantees across Google/network failures. The uncertain-send lock is intentionally conservative. Review remaining direct RPC paths and run multi-session race tests before expanding access.

Product judgment: suitable for a closely supervised release-coordination pilot, not yet a proven replacement for a management company's entire operating process. Investor judgment is conditional: the proposed advantage is fewer missed deadlines and follow-up work, but paid demand, retention, time saved, distribution, market size and defensibility have not been established by this repository. A useful next experiment is 3–5 managers using real projects for four weeks; measure time to first usable plan, corrections per import, repeat weekly use, admin time saved and actual willingness to pay. These are proposed validation criteria, not measured results or YC admission criteria.

## Shared counts and workspace dates

Apply `202610140033_workspace_timezone.sql` after 032. This adds the workspace timezone with the requested America/Chicago default. It does not modify task deadlines, release dates, contact recipients, or manager assignments. Existing Google calendars are not edited automatically; new calendars use the workspace timezone. Date-only deadlines remain all-day calendar dates, not timestamps to shift between zones.

`lib/workspace/rules.ts` defines the rules used by the server workspace loader, follow-up actions, Calendar actions, and page filters:

- Open: active, accessible task with status other than Complete. Archived/inaccessible parents exclude their children, including tasks linked indirectly through a project.
- Overdue: open task with a confirmed date strictly before the workspace's current day. Due today and undated tasks are not overdue.
- Completed: active, accessible task with status Complete. Tasks and project progress retain these; follow-ups and Calendar omit them.
- Missing manager: open task with no inherited artist-manager assignment. A general task must first be linked to an artist. A follow-up contact is not the manager.
- Missing recipient: no selected contact or no nonblank email. Count this independently of uncertain send state.
- Actionable overdue follow-up: overdue, manager assigned, recipient email present, and no uncertain send. This does not imply permission to send, no previous message, or no reply; review message history before sending.
- Active project: not archived or Released, including undated projects and tours/campaigns.
- Upcoming release: active Single, EP or Album with a date today or later. Today displays the next five; Projects' Upcoming filter shows all.
- Next seven days: today through six days later, inclusive.

Dates use America/Chicago daylight-saving rules. The open workspace checks day rollover every 30 seconds; follow-up history reloads after rollover or refreshed workspace data. Civil-date formatting uses UTC internally only to preserve the stored date without a day shift. Activity/send timestamps are displayed in workspace time.

Calendar shows dated projects and open dated tasks, including past dates for context. Google sync covers a selected project, while general tasks remain in Dopio. Project progress is linked-task completion, independent of manually selected project status. The Calendar sync badge describes this visit only and clears when its project/task versions change.

Follow-up history fails with an explicit error above its 1,000-row limit instead of presenting partial counts. Workspace and follow-up pages retain their existing refresh/error controls. Full activity history remains owner-only.

## Workspace assistant (migration 038)

Apply `supabase/migrations/202610190038_assistant_conversations.sql` once, after 037, using the existing migration procedure. This file has been tested locally; applying it to a hosted project requires administrator approval. It adds private assistant conversations and action receipts, not another date-approval queue. Conversations are author-only, checked against current workspace role and all artists whose context was available. Losing an assignment or changing roles hides affected history. Owners cannot read another member's assistant history. Team conversations remain separate and human team-message text is not automatically sent to AI.

The assistant retrieves RLS-filtered artists, projects, tasks, briefs, contacts, personal imported emails, accessible approvals, owner-visible activity and structured team events. Each table is paginated up to 5,000 records, then up to 100 sources are ranked for the question. Coverage notices disclose truncation and retrieval errors; absence is not evidence that a record does not exist elsewhere. Source links come from server-retrieved IDs, never model URLs. Workspace-day statistics use the same Central/default workspace timezone rules as the rest of the product. Retrieval is lexical, not exhaustive semantic search; broad answers should be checked against the visible coverage notice.

Optional Gmail search reads at most five matching messages from the connected member's last 90 days; it does not import, modify, mark read or send them, and excludes attachments. Email bodies are untrusted input. Calendar retrieval reads up to 250 events from the member's Dopio-created Google calendar, filtering to current accessible local record IDs. It cannot read arbitrary personal calendars under the existing OAuth scopes. Reconnection/provider errors are shown rather than treated as empty successful results. No OAuth scopes or external credentials are changed by migration 038.

Supported reviewed commands:

- Create tasks or change their title, deadline, status and notes. Preserve artist/project ownership. Task, artist and project versions must still match; date constraints, audit triggers and team updates remain active.
- Create artists (owner only), edit artist names/status, replace artist release-context notes while retaining contacts/preferences, and edit project notes.
- Create release plans using the existing atomic plan RPC. Revise release title, format, date and existing task schedules through the existing revision reviewer and `revise_release_plan` RPC.
- Draft an email using a supplied contact, explicit address or retrieved sender. The existing email composer requires review and explicit confirmation; Gmail acceptance is not recipient delivery. Drafts are ordinary emails, not guaranteed threaded Gmail replies.
- Preview and explicitly approve creation/update of managed Calendar events using the existing stable event IDs, preview tickets, sync receipts and partial-failure handling.

Multi-step requests produce individual confirmation cards. Read-only retrieval runs automatically; shared-record writes and external actions require approval. Task/record commands carry stable request UUIDs and database receipts. Retrying a committed command returns its record; changing a reused request's payload is rejected. Successful steps remain committed if a separately approved later step fails. Coordinated release/task revisions remain a single transaction. A failed action remains retryable; stale proposals require a new review. Tool outcomes are saved with conversation history, while database receipts are authoritative if history saving fails.

The chat saves up to 60 messages (300 KB of serialized content) per conversation and lists the 50 most recently updated accessible conversations. It sends the latest 28 turns to AI. New messages use validated structured output, with visible retrieval/save progress rather than token-by-token streaming. Generated prose can still contain interpretation errors; validation verifies citation identity and command targets, not every natural-language claim. The app does not run unattended background agents, auto-approve proposals, or silently send emails/calendar invitations.
